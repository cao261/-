- **问题**：`docs/LLM_CONTRACT.md` §2.1 把"非视觉模型编造整张表"定为**红线**（数值一个都不对，用户会照着算）。守卫只检查入口名字，而 `llm.chat` 内部还有"自定义模型失败 → 退回主模型"这一跳，主模型**从不接受视觉检查**。而 `_looks_like_markdown_table()`（app.py:1825）只判"有没有竖线"，伪造的表照样通过。
- **触发条件**（代理实测复现调用序列）：
  1. `LLM_MODEL_NAME=deepseek-v4-pro`，界面选**"跟随当前设置"**（默认）→ `m_name is None` → `if m_name and ...` **整条守卫被跳过** → 表格直接发给非视觉主模型。实测输出：`实际调用序列 [('deepseek-v4-pro', False)] → 表格由【不支持视觉】的模型产出: True`

- **建议修法**：把视觉检查**下沉到实际发出去的模型这一层**——在 `llm.chat` / `_invoke_model` 加 `require_vision: bool`，在**每一次** provider 调用前校验 `model_supports_vision(cfg["model"])`，不通过就跳过该 provider 或直接失败。app 层的前置检查保留（用于决定"换哪个视觉模型"），同时补上 `m_name is None` 的默认路径。

### 3.2 🟠 H-1　读路径无 Host 白名单 → DNS rebinding 可读走整个 vault（本轮已独立复现）

- **位置**：`microbench/app.py:362-440`（CSRF 守卫）、`app.py:381`（`_SAFE_METHODS` 短路）、`app.py:385` / `412-424`（Host 头只被用来推算端口，**从不校验合法性**）
- **证据**：
```python
# app.py:381
if request.method.upper() not in _SAFE_METHODS:   # GET/HEAD/OPTIONS 直接跳过整个守卫
    ...
    host_header = request.headers.get("host") or ""
    allowed_ports.add(int(host_header.rsplit(":", 1)[1]))   # Host 只用来算端口
```
- **问题**：守卫注释（app.py:369-372）声称"defeats DNS rebinding (evil.com resolving to 127.0.0.1), because the browser would send `Origin: https://evil.com`"——**这个推理只对写操作成立**。GET 不进守卫，uvicorn 也不校验 Host，攻击者页面（`http://evil.com:5000` rebind 到 127.0.0.1）在浏览器眼里与服务**同源**，`fetch()` 读响应无 CORS 障碍。
- **实测复现**（审计员独立执行，非代理结论）：
```
GET /api/stats         Host: evil.com:5000  → 200  {"literature_total":23,...,"pdf_total":27,"annotation_count":24}
GET /api/sync/status   Host: evil.com:5000  → 200  {"root":"C:\\Users\\30461\\Nutstore\\1\\我的坚果云\\MicroBench同步",...}
GET /api/vault/literature Host: evil.com:5000 → 200  完整文献列表 + 路径
POST /api/paper/save   Host+Origin: evil.com → 403  ← 写操作确实被挡住
```
- **影响**：**未发表的研究笔记、全部论文 PDF、快照清单、同步目录绝对路径（含 Windows 用户名）**可被任意网页在用户打开工作台时读走。写操作（改 vault、烧 LLM 额度）仍被 403 挡住——**这条边界成立，风险限于读**。
- **建议修法**：加最外层 Host 白名单中间件，只接受 `127.0.0.1[:port]` / `localhost[:port]` / `::1[:port]` / 本机 LAN IP[:port]；LAN 模式把启动脚本打印的那个 LAN IP 一并加入。

### 3.3 🟠 H-2　files 通道的墓碑**不可逆**：删掉的 PDF 放回原处，对方设备**永远**拿不到

- **位置**：`microbench/app.py:4881-4906`（快判 / "内容没变"分支）、`app.py:4924`（只有内容变化才写 `deleted=False`）、`app.py:4977-4994`（pull 侧认墓碑）
- **证据**：
```python
# 4881-4891 快判：size/mtime 都没变 → "unchanged"，什么都不做
if (old.get("size") == st.st_size and abs(...) < 1e-6 and (...)):
    res["unchanged"] += 1; continue
# 4899-4906 内容没变（sha256 相同）→ 只更新清单，**不动 deleted，也不重建 blob**
if old.get("sha256") == digest:
    old.update({"size": st.st_size, "mtime": st.st_mtime}); continue
# 4924 只有"内容真的变了"才写 deleted=False
```
- **问题**：墓碑 `deleted=True` 是**粘的**。用户"删错了又放回来"（回收站恢复 / 手动拷回 / 重新下载同一篇）后，push 走的是 "unchanged" 分支 → 清单里 `deleted` 保持 True；而 pull 一旦看到 `deleted` 就 `continue`，**永远不会还原**。
- **触发条件**（沙箱实测全链路复现）：
  1. 发布 `01_Literature/cat/2024_Paper.pdf` → `deleted=False, blob=True`
  2. 删本地 → push → `deleted=['...2024_Paper.pdf']`，meta `deleted=True`
  3. **把同内容文件放回** → push → `published=[] updated=[] unchanged=1`，**meta.deleted 仍是 True**
  4. 对方 pull → `{'restored': [], 'retained': ['...2024_Paper.pdf']}` → **一个都没还原**（哪怕 blob 实体还在）
- **影响**：PDF 本体在同步通道里**永久失效**，两台设备从此看不到同一份文件；用户视角是"文件还在、同步显示成功、另一台就是没有"。现有测试 `tests/test_sync_files.py:202-213` 只验证"墓碑不联动删本机文件"，**没覆盖"放回后应复活"**。
- **建议修法**：在"unchanged / 快判"分支里显式清墓碑（文件在本机 = 没删），并补断言：放回后 `meta["deleted"] is False`、对方 `pull` 能 `restored`。

### 3.4 🟠 H-3　墓碑 pull 会删掉共享目录里的 blob 实体，而 owner 的后续 push **不会重建** → 清单说 `blob=True` 实体却不在

- **位置**：`microbench/app.py:4989-4993`（pull 侧删 blob）、`app.py:4883-4885`（push 侧快判条件）
- **证据**：
```python
# 4977-4994  pull 侧看到墓碑
if meta.get("deleted"):
    if blob.exists():
        try: blob.unlink()          # ← 实体没了，清单还在
        except OSError: pass
    continue
```
```python
# 4883-4885  owner 再 push 时的快判条件
and (blob.exists() or old.get("blob") is False)):
#   blob 不存在 且 meta.blob 仍是 True → 快判不成立 → 落到 sha256 分支
#   → 内容相同 → "unchanged" → 既不复制 blob，也不改 meta.blob
```
- **问题**：这是**清单与实体不一致**的稳定状态：`meta.blob=True` 而 `files/<safe>.pdf` 不存在。owner 端没有任何逻辑会把它补回来（只有内容 sha256 变化才走重传分支），于是"放回去 / 重新下载同一篇"也救不回来。
- **触发条件**（沙箱实测）：发布 → 删本地 → push 墓碑 → 对方 pull（**blob 被 unlink**）→ owner 放回并 push → `unchanged=1`，**blob 仍不存在**、`meta.blob` 仍为 True → 第三台设备 pull → `retained`，**0 个文件**（"云端已释放实体"分支）。
- **影响**：PDF 从共享通道**彻底消失且不可自愈**；`/api/sync/status` 的 `blob` 显示 False 但清单写 True，任何按清单做的逻辑都会误判。
- **建议修法**：pull 侧删 blob 时同步把清单 `blob` 置 False；push 侧在"内容没变但 blob 缺失且 `meta.blob` 为 True"时**重建 blob**；补一条通用不变量测试：`meta["blob"] == blob_path.exists()`。

### 3.6 🟠 H-5　漏译检测对"PDF 抽取出来的换行式英文"**实测 0 命中** —— 而这正是最常见的漏译形态

- **位置**：`microbench/translation.py:417-418`（正则）、`translation.py:427`（排除词表）
- **证据**：
```python
# translation.py:417 —— 词与词之间只接受 [ \t]，**不接受换行**
for m in re.finditer(r"[A-Za-z][A-Za-z\-']*(?:[ \t]+[A-Za-z][A-Za-z\-']*){%d,}" % (min_words - 1), text):
```
- **问题**：`translation.py` 自己的注释（`_split_oversized` 第 110 行）写明"**PDF 抽取的文本保留了论文的换行**"，而 `paper_text` 的抽取结果就是这种带硬换行的文本。模型漏译一整段时正文长这样：
```
the dielectric properties of the
ferroelectric thin films were
investigated using a modified
pulse deposition technique and
...
```
  每行都不足 8 个词 → 正则一个都匹配不上 → **漏译被判定为"没有漏译"**。
- **审计员独立复核**（`C:\Users\30461\.minimax\tmp\leak_check.py`）：
```
A. PDF 换行式英文（每行 <8 词，最常见形态）  -> 命中 0 段   ❌ 未检出
B. 单行整段英文（对照组）                    -> 命中 1 段   ✅ 检出
C. 换行式 + 含 'Table '                     -> 命中 0 段   ❌ 未检出
D. 换行式 + 含 'doi'                         -> 命中 0 段   ❌ 未检出
E. 整段被模型丢弃（无任何英文残留）            -> 命中 0 段   ❌ 未检出
```
- **附带盲区**：
  - **整段被模型丢弃（不是不译，是直接跳过）→ 完全无感**。全链路**没有任何段落数比对或长度比对**；响应里仍回 `"untranslated_runs": 0`（app.py:3980）→ 用户看到"0 段未翻译"就相信页面完整。
  - **排除词表会整段跳过漏译**：正则 `@|Fig\.|Table\s|Eq\.|doi|https?://|arXiv` 命中即 `continue`。学术论文里 "table / Fig. / Eq." 出现在正文中的频率极高。
- **影响**：漏译直接进用户界面，且系统**声称**已校验完整性——正是用户反复反馈的"有的翻译有的不翻译"。`tests/` 下对 `find_untranslated_runs` 的测试数量为 **0**。
- **建议修法**：① 正则分隔符改 `[ \t\r\n]+`（或调用前折叠连续空白）；② 排除词表从"整段豁免"降级为"只豁免命中位置附近的片段"；③ **增加段落数 / 长度比校验**（原文按 `\n\n` 切段数 vs 译文段数、译文长度 ÷ 原文长度），低于阈值即判漏译并触发重译——这是目前唯一能覆盖"整段被丢弃"的手段；④ 漏译未修复时不要再回 `"untranslated_runs": 0` 这种"已校验通过"的语义。

### 3.7 🟠 H-6　表格读图路径没有 deadline，一张坏表最坏能把一次翻页请求挂 18 分钟

- **位置**：`microbench/app.py:3885`（`llm.chat` 调用）、`app.py:3872`（`_prepare_tables` 调用点）、`app.py:3882`（deadline 计算点）
- **证据**：
```python
# app.py:3885 —— timeout=180，但没有 deadline=
raw = await asyncio.to_thread(
    llm.chat, messages=[...], max_tokens=4000, temperature=0.0,
    timeout=180, disable_thinking=..., model_name=m_name, force_fallback=m_fallback,
)
# app.py:3872-3882 —— 表格读图发生在"翻译总时限"开始计时之前
page_text, table_map = await _prepare_tables(...)
deadline = time.monotonic() + _translation_deadline_seconds(req.model)   # 3882，晚于表格
```
- **问题**：`llm.chat` 的 `deadline` 形参（llm.py:1929）是唯一能把"重试 + 抬预算重试"整条链路兜进固定时限的机制。表路径没传 → 每次尝试都是满 180s，而 `chat()` 的上游调用预算为 6 → **最坏 6 × 180s = 18 分钟**，且这段等待发生在翻译总时限（默认 180s）**开始计时之前**，`_translation_deadline_seconds` 完全管不到它。

### 6.2 两条失败的定性：**环境限制，不是代码缺陷**

1. 探针的**源码断言 6 项全 PASS** → `index.html` 里的手写笔迹逻辑本身正确；
2. 失败发生在 `run_probe()` 的浏览器阶段：`探针没返回结果（DOM 0 字节）`；
3. 独立复现：`msedge.exe --headless --dump-dom <任意页面>` → **输出 0 字节**；

4. 本机 Edge 版本 **157.0.4341.42** → 新版 Chromium 已移除旧 headless 的 `--dump-dom` 输出能力。

**结论：环境限制。** 但后果是真实的，且属于项目纪律问题：

- 这 2 条测试是 **2026-10-29（`3dac233`，即当前 HEAD）引入**的，**从未在本机通过**；
- AGENTS.md §1 的硬性要求是"**全绿才算做完**" → **当前 HEAD 不满足自己的质量门，却已推到 `origin/main`**；

  一旦 `auto_sync` 恢复运行，这两条会**静默卡死整条跨设备代码同步管道**；
- `microbench/_test_desktop_ink_render.py:37-41` 的 `find_browser()` 在**完全找不到浏览器**时返回 SKIP，
  但新版 Edge **存在** → 走进真实渲染分支 → 误报 FAIL。

## 二、根因（三条叠加，都做了实测取证）

### 1. 逐页串行认字（主因）

`upload_pdf` / `open_vault_pdf` 原来对**每一页**调一次符号认字
（`glyphs.resolve_glyphs_sync`），每页一次多模态 HTTP 请求。

实测（36 页的 JAP 综述，35 页含符号）：

| | 修复前 | 修复后 |
|---|---|---|
| 打开耗时 | **8 分钟仍未返回**（我手动取消） | **5.5s** |
| 多模态调用次数 | 35 次**串行** | 0 次（打开不调模型）|

单次认字实测 29~48s（主模型 29s / 备用 Agnes 48s）。

### 2. 形状指纹词典永远命不中（还带误判风险）

旧词典主键是"16×16 拉伸位图 + 汉明距离阈值 40"。
全库 24 篇 / 6184 个字形实例实测：

| | 同符号不同实例 | 异符号之间 |
|---|---|---|
| 拉伸 16×16 | 组内差 中位 **61** | 组间差 中位 **74** |

→ 两者**重叠** → 阈值 40 既命不中，又会把 ≈ 认成 ≥
（异符号误判率 **26~41%**）。

**证据链**：我曾尝试用旧形状词典去推语义键，结果 **20 个不同语义键全被映射成 `÷`**，
肉眼核对发现 `MathematicalPi-Three|16` 明明是 `)`。
→ **旧形状词典本身是污染的**，已回滚（`logs/glyph_dict.json` 里 30 条旧条目保留但不再用于推语义键）。

### 3. 认字失败触发全局降格，连累翻译

日志里反复出现：
```
[MicroBench] ⚠️ 主模型触发降格 (no_output): ... 已自动切换至备用模型 [60s 后自动恢复]
[MicroBench] 符号认字失败（退回 [?]）: 备用模型 (agnes-3.0-flash) 调用失败: ...
```
认字是**后台小任务**，它的失败不该把用户正在跑的翻译也拖去备用模型。

## 三、做了什么

### 3.1 语义键作词典主键（核心）

```python
semantic_key(font, cid) -> "MathematicalPi-Three|2"   # 去掉 XXXXXX+ 子集前缀
```
- 全库只有 **101** 个不同语义键（对比：6184 个字形实例）
- 其中 **76 个跨 ≥2 篇论文**重复 → 认一次长期命中
- 实测同语义键**跨文档**形状距离中位 **0** → 语义键确实稳定

### 3.2 形状指纹降级为二级校验

- 新增 `_shape_bits_stable()`（等比补白，不拉伸）→ 跨文档同键差中位 0
- 阈值 `_SHAPE_GUARD_MAX_DIFF = 96`（同键实测最大差 81 → 不误杀同符号）
- 形状区分不开不同符号（异符号中位 47）→ 只能当"极端不像就拒绝"的兜底

### 3.3 整篇一次解析 + 打开不调模型 + 后台补齐

```
打开/上传  → resolve_document_glyphs(recognize=False)  → 只查词典 → 亚秒级
             └→ _schedule_glyph_backfill()              → 后台线程认字 → 填词典
按页翻译   → _resolve_page_glyphs()                     → 只查词典
拉取全文   → fetch_full_text(recognize=False) + 后台补齐
```
- 后台补齐用 `isolated=True` → `llm.chat_isolated()`（只打主模型、**不改全局降格状态**）
- 词典已覆盖该论文全部符号时**不重复认**（守卫，省配额）

### 3.4 顺手修的两个真 bug（测试抓出来的）

1. **内部标记外泄**（§4.6 红线）：回填逻辑原来在 `try` 里 →
   打开 PDF 失败就整段跳过 → `⟦G:n⟧` 原样进 prompt → 模型照抄/瞎编。
   → 回填移进 `finally`，任何路径都不漏。
2. `resolve_document_glyphs` 里批量循环解包 3 个值但 items 是 2 个 → 整批认字静默失败。

### 3.5 前端

三个入口（上传 / 仓库打开 / 拉取全文）都加了 3 秒一次的进度提示 + 耗时显示，
不再"假装卡死"。

## 五、⚠️ 明天的待办（可选改进，不影响"不卡住"）

### 5.1 裁图带到了相邻字符 ✅ 已修（2026-10-26）

**现象**：肉眼核对对照图发现裁出来的图里**带着邻居字符**：

```
s:MathematicalPi-One|1   → 裁出 "ω𝑓"   （应该是单独的 ω）
s:MathematicalPi-One|5   → 裁出 "ε:"   （应该是单独的 ε）
s:MathematicalPi-One|7   → 裁出 "μ𝑜"
```

**原因**：`_render_glyph` 用 `±1.0pt` padding 裁剪。窄字形只有 2~3pt 宽，
±1pt 横向就吃到了旁边的字符。

**标定数据**（46 个语义键，判据 = 别的字形有多少面积落进裁剪框）：

| padding | 混入邻居的字形数 | 平均混入数 |
|---|---|---|
| 1.0（旧） | 14 / 46 | 0.35 |
| 0.35 | 11 / 46 | 0.28 |
| **0.25（采用）** | **9 / 46** | **0.24** |
| 0.10 | 7 / 46 | 0.17 |

→ `_GLYPH_PAD_PT = 0.25`（接近最小混入，又留余量防切字形：
实测 pad=0 时墨迹左溢 ≤0.75pt，是抗锯齿边缘，不会切字形）。

**已做**：
1. ✅ 改 `_render_glyph` 用 `_GLYPH_PAD_PT = 0.25`
2. ✅ **重算词典里所有语义键条目的形状基准**（渲染变了 → 指纹变了 →
   `get_verified()` 会把旧条目全判为"形状对不上"而**全部误杀**）→ 回读 30/30
3. ✅ 重新认了一遍 → 词典从 30 条涨到 **70 条**语义键
4. ✅ 护栏：`tests/test_glyph_padding.py`（8 条，已反向验证：
   padding 改回 1.0 → 变红）

**效果**：JAP 综述里 `[?]` 残留 **1226 → 303**（-75%）。

### 5.2 模型认不出"括号类"符号 ✅ 已修（2026-10-26）

**根因有三个**（前两个是设计问题，不是模型能力问题）：

1. **提示词没给候选清单** → 模型对括号/竖线不自信 → 大量答 `?`
   （实测 22 个语义键 → 22 个全是 `?`）
   → 给出候选清单后：**认出数 7/71 → 40/71**，括号类全部正确
2. **白名单里没有括号类** → 模型**认对了也会被丢弃**（`put()` 拦掉）
   → 已在 `ALLOWED_SYMBOLS` 补 `()[]{}|‖⌈⌉⌊⌋` 与 `≧≪≫`
3. **清单里有些符号不在白名单** → 模型选了也被丢，那次调用白费
   → 有测试钉死：`test_hint_prompt_symbols_are_all_whitelisted`

### 5.3 词典里 30 条旧形状条目 ✅ 已清（2026-10-26）

- 旧条目是"形状指纹 → 符号"，而形状指纹已被证明不可靠（异符号误判率 26~41%）
- `GlyphDictionary.get()` 的"形状最近邻"兜底**已删除**
- 文件已清理为**纯语义键 70 条**（旧条目不再参与任何匹配）
- ⚠️ 两台设备共用这份文件（坚果云）→ 对方设备拉到新代码后，
  旧条目没了也不影响（只是少一层本来就不可靠的兜底）

### 5.4 剩下的 31 个语义键（模型能力边界，可不管）

未认出的实例只占全库 **5.9%**（6184 个实例里 365 个）。最大一项是
`TeX_CM_Maths_Symbols|0`（94 次，`2026_Sensors_&_Actuators_A` 那篇）。

这批是**大括号的笔画碎片**（`MathematicalPi-Three|9..16` 是 28~34pt 高的
分段笔画）—— 单独看确实不像一个完整符号，模型答 `?` 是**诚实且正确**的
（符合"宁可空着也不能指错"）。

可选改进（都不是必须的）：
- 把同一字体的多个碎片**拼在一起**再让模型认（`{` 在 TeX 里是由多段拼的）
- 换更强的多模态模型
- 就这样留着（用户看到的是 `[?]`，但不影响阅读）

## 3. 详细发现

### 3.1 🔴 H-1　pytest 会写进用户真实的坚果云同步目录（已实测复现）

**位置**
- `tests/conftest.py:65-114`（`sandbox` fixture 只重定向 `BASE_DIR`）
- `microbench/app.py:3941-3957`（`_sync_root()`）
- `microbench/llm.py`（import 时 `load_dotenv(..., override=False)`）
- `tests/test_sync_regressions_2026_10_25.py:281-289`（**唯一漏网的测试**）
- `microbench/auto_sync.py:177`（每 2 小时自动跑 pytest）

**根因（三层叠加）**

1. `microbench/llm.py` 在 import 时 `load_dotenv(override=False)` → `.env` 里的
   `ANNOTATIONS_DIR` 被灌进 `os.environ`。`conftest.py` 只钉了 `SYNC_PDF_BODY`
   （第 39 行 + autouse fixture 第 82 行），**没钉 `ANNOTATIONS_DIR`**。
2. `app.py:3948` 的 `_sync_root()` 第一优先级就是 `os.getenv("ANNOTATIONS_DIR")`
   → 测试进程解析到**真实**的坚果云目录。
   而即使钉死这个变量，`_sync_root()` 还有第二个分支（`app.py:3954`）会**自动探测
   坚果云云端沙箱**，第三个分支（`app.py:3957`）才是 vault 内的 `_同步`。
   ⇒ **只钉环境变量不够，必须钉函数本身。**
3. `sandbox` fixture 只 `monkeypatch.setattr(gen_mod/app_mod, "BASE_DIR", tmp_path)`，
   **没有** patch `_sync_root` → 同步层整体漏在沙箱外。

**实测证据（本轮亲自复现）**

```
# import microbench.llm 之后
ANNOTATIONS_DIR in os.environ: True
ANNOTATIONS_DIR = C:/Users/30461/Nutstore/1/我的坚果云/MicroBench同步
_sync_root() = C:\Users\30461\Nutstore\1\我的坚果云\MicroBench同步
里面是真实数据: annotations(2) / files(27) / progress(3) / snapshots(4)
```

对同步目录做「路径 + 大小 + mtime + sha256」指纹，**跑一遍 `pytest tests -m "not slow"`** 前后对比：

```
before files=36  after files=36
新增: 0   删除: 0   内容变化: 1
  ~ files/demo.json  64B/62f71ee3d2005447 -> 64B/94eaa8e39bd62617
```

`files/demo.json` 的来源是 `tests/test_sync_regressions_2026_10_25.py:284`：

```python
app_mod._write_file_meta("demo", {"paper_id": "demo"})   # ← 没 patch _sync_root
```

同文件里其它同步测试（`test_sync_files.py:19`、`test_sync_regressions_2026_10_25.py:98`）
**都正确 patch 了 `_sync_root`** —— 说明这是**单个测试的遗漏**，但根因是系统性的。

**当前实际损害（诚实说明）**
- `files/demo.json` 被反复改写 → mtime 抖动 → **坚果云反复重新上传**；
  另一台设备的 `/api/sync/files/status` 会出现幽灵条目。
- 暂时**不会丢数据**：pull 循环 `app.py:4371-4373` 遇到缺 `relative_path` 的条目会
  `continue` 跳过；push 循环只处理 vault 里的真实 PDF。
- `auto_sync.py:177` 每 2 小时自动跑 pytest → **无人值守地**持续写入。

**潜在风险（这才是要害）**
`/api/sync/files/release {"all": true}` 会**删除**共享目录里的 PDF blob，
`/api/sync/files/propagate_delete` 会给对方 PDF 打墓碑。
只要将来有任何一个新测试忘了 patch `_sync_root`，
它就是在**删用户的跨设备数据**，而 `conftest.py` 自己的注释已经写明了这条原则：

> "The user's real vault holds real research notes; a test that writes to it
> is a test that can destroy work."

**修法**

```python
# tests/conftest.py —— 加一个 autouse fixture，把同步根钉到临时目录
@pytest.fixture(autouse=True)
def _pin_sync_root(tmp_path, monkeypatch):
    """同步层必须和 BASE_DIR 一样被沙箱化。

    _sync_root() 有三个分支：ANNOTATIONS_DIR 环境变量 / 坚果云云端沙箱自动探测 /
    vault 内目录。前两个都指向**真实**的跨设备数据。只钉环境变量不够——
    必须钉函数本身。
    """
    from microbench import app as app_mod
    shared = tmp_path / "_sync_shared"
    shared.mkdir(parents=True, exist_ok=True)
    monkeypatch.setattr(app_mod, "_sync_root", lambda: shared)
    monkeypatch.setenv("ANNOTATIONS_DIR", str(shared))
```

再加一道护栏（防止将来又漏）：

```python
def test_sync_root_never_points_at_real_data(sandbox):
    from microbench import app as app_mod
    root = str(app_mod._sync_root())
    assert "Nutstore" not in root and "我的坚果云" not in root, \
        f"同步根指向了真实云端目录: {root}"
```

**顺带清理**：删掉 `files/demo.json`（测试产物，不该在云端目录里）。

### 3.2 🟠 H-2　SSRF 守卫是「检查时点判定」，DNS 重绑定可绕过，响应还会回显

**位置**：`paper_fetcher.py:66-110`（`_assert_public_http_url`）、
`paper_fetcher.py:113-139`（`_safe_redirect_chain`）、`paper_text.py:1802/1839-1896`

**问题**
守卫用 `socket.getaddrinfo` 解析一次、把地址收进 `addrs` **校验完就丢弃**，
没有把 IP 钉到连接上；`requests`/urllib3 在**连接时再解析一次**。
独立审查插桩实测：同一次请求 `getaddrinfo` 被调用 **2 次**。

更糟的是：本机 `HTTP_PROXY=127.0.0.1:65532` 存在时，`requests` 根本不本地解析目标域名
——**由代理解析**。此时守卫的本地 DNS 判定与真实落点**零关联**。

守卫 docstring 自称能挡 rebinding（`paper_fetcher.py:84-86`），实际只挡得住
「字面 IP」和「首答为内网」两种。

**响应回显（可利用的落点）**
`POST /api/paper/fetch_full` body `{"identifier":"http://attacker.test/x.pdf"}`
→ 守卫放行 → 抓到内网 PDF → `extract_text_from_pdf` 的**全文**在
`app.py:2424-2449` 的 `sections` 里**原样回显给客户端**。

**修法**
1. 解析一次 → 校验 → **把连接钉到已校验 IP**（把 URL 的 host 换成已校验 IP +
   显式设 `Host` 头；HTTPS 还要固定 SNI），或自建 `HTTPAdapter` 在 `send()` 里先连已校验 IP；
   每个 redirect hop 重做同样动作。
2. 对用户可控 URL 强制 `proxies={"http": None, "https": None}`
   （AGENTS.md §4.9 已记过这条教训，这里同样适用）。
3. `download_arxiv_pdf`（`paper_fetcher.py:240-246`）的 `allow_redirects=True`
   也没过守卫，虽然 host 被 `_normalize_arxiv_id` 钉在 arxiv.org、实际影响小，
   但和其它路径的严格度不一致，建议统一。

**置信度**：双次解析**已证实**；端到端利用需攻击者可控 DNS → 实际可利用性**高度可疑**。

### 3.4 🟡 M-2　`GET /api/paper/formula_image` 阻塞事件循环，无并发上限，跨站可触发

**位置**：`app.py:1593-1646`（端点）、`app.py:1383-1415`（`_pdf_clip_png`）

`app.py:1634` 在 **async 函数里同步调用** `_pdf_clip_png`（PyMuPDF 渲染）→
渲染跑在**事件循环上** → 一次请求就把整个工作台（含全部 SSE 流）卡住。
对比：表格路径 `app.py:1485` 已经用了 `await asyncio.to_thread(_pdf_clip_png, ...)`，
**公式路径漏了**。

其它问题：
- `max_pixels=4_000_000` 只限制**单次**输出，不限制并发；
- 全项目**没有任何 HTTP 层限流**（`llm.py` 的限流只管上游模型）；
- `scale` 上限 8（`app.py:1599`）→ 单请求约 4M px 栅格化；
- GET 属 `_SAFE_METHODS`（`app.py:174`）→ `csrf_origin_guard` **整条跳过**
  → 任意网页 `<img src="http://127.0.0.1:5000/api/paper/formula_image?...">` 可触发。

**修法**：`await asyncio.to_thread(_pdf_clip_png, ...)`；
给 `/api/paper/formula_image` + `/api/paper/serve_pdf` 加进程内信号量与每 IP 令牌桶。

### 3.6 🟡 M-4　仓库位于 `D:\Desktop`，ACL 全程继承 `Authenticated Users: Modify`

**实测**

```
D:\  →  D:\Desktop  →  D:\Desktop\杂物  →  …  →  仓库根
NT AUTHORITY\Authenticated Users : Modify, Synchronize   ← 全程继承
BUILTIN\Users                   : ReadAndExecute
```

**后果**
1. **本机任何其他用户都能读出 `logs/lan_token.txt`**（LAN 共享口令）；
2. **也能改写 `microbench/app.py`** —— 服务以当前用户运行 → 等价于代码执行。
   默认的 `%USERPROFILE%` 不会有这个继承（只给本人 + SYSTEM + Administrators）。

**修法**：把仓库/vault 挪进 `%USERPROFILE%`；或显式收紧根目录 ACL
（`icacls "D:\Desktop\杂物\琐事\个人工作台" /inheritance:r /grant "%USERNAME%:(OI)(CI)F" /grant "SYSTEM:(OI)(CI)F"`）。

### 3.12 🟠 H-4　`_safe_base_url` 的兜底分支返回**未脱敏的原 URL**

### 3.13 🟡 M-9　限流器的 `min_interval` 在并发下失效

### 3.19 🟡 M-15　章节视图的「模型名」未转义即写入 `innerHTML`

**位置**：`microbench/static/index.html:5636`（写入点 `index.html:5632` `transEl.innerHTML = ...`）

**链路（逐跳读过代码）**
1. `app.py:654` `model: str = Field(default="", max_length=60)` —— **无白名单校验**；
2. `app.py:658-680` `_resolve_translation_model()`：非 `agnes`、非已配置的自定义模型时
   **原样返回**（`app.py:680 return req, False, req`）；
3. `app.py:2592` `_m_name, _m_fallback, model = _resolve_translation_model(req.model)`；
   `app.py:2759` `actual_model = model`；`app.py:2766` `"model": actual_model` → **原样回显**；
4. `index.html:6100` `_readerState.translationModels[idx] = result.model;`
5. `index.html:5629` `const modelName = ...`
6. `index.html:5636` `` `${modelName ? `[${modelName}] · ` : ""}` `` —— **无 `escapeHtml`**

**实测（本轮亲自验证，并修正了子代理的可达性判断）**

```
POST /api/paper/translate_section  {"model": "<img src=x onerror=alert(1)>", ...}
→ 上游 HTTP 400 → 服务端 502
→ 502 的 detail 里确实带了 payload:
   "LLM 调用失败: 模型 (<img src=x onerror=alert(1)>) 不可用或被拒绝（HTTP 400）..."
```

但前端 `!res.ok` 分支（`index.html:6090-6096`）把 detail 交给 `showToast`，
而 **`showToast` 用的是 `t.innerText = msg`（`index.html:2557`）—— 安全**。
且请求 502 ⇒ `result` 从未生成 ⇒ `result.model` 从未进 `_readerState`。

**结论（修正子代理的判断）**：这条**当前不可利用**。
要让 `result.model` 带 payload 并成功返回，请求里的模型名必须**被上游接受** ——
而 MiniMax 只接受固定模型名，所以现实可达路径只剩「`.env` 里配置了 id 含 HTML 的自定义模型」。
本机 `.env` **未配置任何自定义模型**（已实测）→ 今天打不进去。

**但两处该修（这是重点）**
1. **服务端没有白名单**：`app.py:654` 只限长不限值 —— 任何模型名都会被原样回显给前端；
2. **前端 122 个 DOM sink 里唯一漏转义的一个**：同源的 `e.model`（`index.html:4891`）、
   `meta.model`（`index.html:8114`、`8453`）都转义了，唯独 `5636` 漏了 —— 是**分支遗漏**，不是设计。

**修法**：`index.html:5636` 改成 `${escapeHtml(modelName)}`；
并在 `app.py:654` 加白名单（只允许 `""` / `agnes` / `custom:*` / `TRANSLATION_MODEL_CHOICES` 内的 id），
命中即 400。

## 10. 结论与下一步

**VERDICT = CONDITIONAL PASS**

这个项目的安全底子**比多数同类项目好得多**：路径遍历被彻底堵住（22 条专项 payload 全灭）、
XSS 链路经过多轮加固（122 个 DOM sink 全量归类，只漏 1 处且当前不可利用）、
依赖无 CVE、bandit 干净、配对流程的细节考虑很周到（303 剥离 token、常量时间比较、fail-closed）。
上一轮审计的问题**确实都修好了**。

但有 **4 条 HIGH 是真实存在、且我已逐条实测复现**：

1. **测试会写到用户真实的坚果云同步目录**。当前损害是污染 + 云端反复上传，
   数据损失尚未发生；但它离「删掉 76MB 的跨设备 PDF 实体」只差一个忘了 patch 的新测试。
2. **`probe_primary` 的异常不过脱敏**，而 `requests` 的 `InvalidURL` 消息里含完整 URL（含 userinfo）
   → 点一次「探测升格」就能把 key 送进浏览器。
3. **`_safe_base_url` 的畸形 URL 兜底分支返回原样** → 手写错端口的 base_url 会带着凭据进
   `/api/llm/status`。
4. **SSRF 守卫是「检查时点判定」**，DNS 重绑定可绕过，且抓到的内容会**原样回显**给客户端。

**共同点值得记**：这 4 条里 3 条都是「**上游/异常/配置**这条边界上少了最后一层防护」——
不是核心逻辑写错了，而是**边界没封口**。项目里已经有 `redact_secrets`、`_safe_path`、
`hmac.compare_digest` 这些好工具，只是有几条分支忘了调用它们。

**建议下一步**：先做 P0 的五处（一处 fixture + 一处白名单 + 两处一行脱敏 + 一次清理），
然后按 P1 清单推进。这五处加起来大概十几行代码，但覆盖了「碰真数据」和「泄 key」两类问题。

**需要我直接动手改吗？** 建议分两个批次：P0 先改（改动小、可立刻回归），
P1 涉及行为变更（事件循环卸载、ACL、字体离线化）单独一批。

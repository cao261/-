## 2. 发现的问题

### F0 · 测试会往**用户真实 vault** 里写文件【P0 · 实施过程中发现并已修】

> 这是本轮**最严重**的一条，而且它是在动手修东西的过程中撞出来的 ——
> 审计时只查了「改动本身」，没查「跑测试会不会弄脏用户数据」。

**症状**：跑完全量测试后，真实 vault 里多出两个 PDF：

```
01_Literature/01_Device_TCAD_器件仿真/01_论文原文_PDF/2026_NoModel.pdf          (406 B)
01_Literature/01_Device_TCAD_器件仿真/01_论文原文_PDF/2026_Revert_Check.pdf     (406 B)
```

**根因**：`tests/test_glyph_perf_regression.py` 的两条上传测试
**自己 new 了 `TestClient(app_mod.app)`**，**绕过 `sandbox` fixture** →
`app.BASE_DIR` / `generator.BASE_DIR` 仍是**真实仓库根** →
`/api/paper/upload_pdf` 按 `_safe_path(BASE_DIR, "01_Literature", …)` 落盘，
把 PDF 写进用户的地盘。文件名直接来自测试的 `title=` 参数
（`NoModel` / `Revert Check`），一眼就能看出是测试产物。

**为什么严重**：vault 的 `01_Literature` 是**坚果云 junction** → 这些垃圾**会同步到云端**，
另一台设备也会看到。跑一次测试就在用户的地盘上留垃圾，而用户完全不知情。
这正是 **2026-10-26 审计 P0「测试不再碰真数据」的同型复发** —— 上次修的是别的地方，这次漏了这个文件。

**已修**：
1. 两条测试改用 `sandbox` fixture，并**断言产物落在沙箱里**
   （`landed = list(Path(sandbox).rglob("*Revert*Check*.pdf"))`）。
2. 新增**元护栏** `test_no_test_builds_a_client_without_sandboxing_the_vault`：
   用 `ast` 找出所有**自己** new 了 `TestClient` 的测试函数，
   它们的参数里必须有负责重定向 vault 的 fixture（`sandbox` / `env` / `vault`）。
   再有人这么写，立刻红。
3. 已把本次跑测试留下的两个垃圾 PDF 清掉（走回收站，可恢复）。

**反向验证**：撤掉那条测试的 `sandbox` → 元护栏立刻红 ✓。

> ⚠ **给用户的一句话**：这两个文件是我这轮跑测试时产生的，已经清掉了。
> 清理走的是坚果云的**真实目标**（junction 挡住了对逻辑路径的删除，
> 工具明确要求对 link target 操作）。

### F2 · 「缺 KaTeX 拒绝导出」那条护栏是**环境依赖**的假护栏【中】

`tests/test_audit_2026_11_09.py:277` 的 `test_export_tablet_refuses_missing_katex_and_keeps_previous`
断言 `export_tablet(...) is False`。但 `export_tablet` 在**没有笔记**时也会返回 False
（`microbench/export_offline.py:1405` 「没有找到任何笔记」）。

对照实验（在退回 KaTeX 检查的副本上）：

| vault 里有笔记吗 | 撤掉 KaTeX 检查后该护栏 |
|---|---|
| 没有（干净 clone / CI / 新设备） | 🟢 **照样绿 —— 护栏失效** |
| 有（本机 23 篇） | 🔴 红 —— 护栏生效 |

也就是说：**在有笔记的机器上它是对的**（本轮实测 stderr 确实是
「[导出器] 缺少 KaTeX 资源，拒绝导出」）；**但在空 vault 上它保护不了任何东西**。
换个干净环境重跑就发现不了有人把 KaTeX 检查删了。

**修法**：给测试打一个最小 vault 夹具（造一篇 `01_Literature/x.md` 进去），
或直接断言 stderr 里出现「缺少 KaTeX」而不是只断言返回值 False。

### F4 · P1-1 的「加锁」那半截没做【中】

上一轮 P1-1 给的修法是两半：
「换 `_read_json_or_quarantine`；**按 paper_id 分桶 `threading.Lock` 包住读-合-写**」。

实测 `microbench/app.py` 全文**没有任何 `threading.Lock` / `asyncio.Lock`**。
第一半（隔离读）做了，第二半（锁）没做。

**影响**：同一个 `paper_id` 的快照**并发保存**（双标签页 / 事件循环与线程池同时写）
仍然会丢页——这正是 P1-1 想解决的那个场景。锁没加 = 治了一半。

**修法**：`app.py` 里按 `safe_id` 建一个模块级 `dict[str, threading.Lock]`（配
`defaultdict(threading.Lock)`），把 `api_pdf_snapshot_save`（`app.py:4238`）的
读-合-写整段包进去。

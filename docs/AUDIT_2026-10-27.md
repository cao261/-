## 0. 一句话结论

**这一轮抓到的东西，和前几轮不是一个量级。**

前三轮审计的结论都是「核心逻辑没写错，是**边界没封口**」；这一轮不一样 ——
**有四条缺陷直接打断用户的主线工作流或真丢用户数据**，而且**都不在服务端的安全边界上**：

1. 🔴 **批注重放会自激**：译文栏的文字选区每 80ms 被洗一次 →
   划词答疑读不到引文 → 「翻论文 → 翻译 → 划词 → 批注」这条主线在最后一步断掉。
2. 🔴 **平板 WebView 离开本地源后仍持有原生桥** → 笔记里的一个外链就能让恶意页面
   删/写用户坚果云里的 vault，并拿平板当 HTTPS 代理打内网。
3. 🔴 **`auto_sync` 快进合并后回退失效** → 坏代码留在 HEAD 且被当成"干净"推给对方。
4. 🔴 **缓存键缺「词典路径」** → 词典变化不触发重抽 → **译文正文与原文不符**。

**性能侧**：上一轮（10-27 早上）修的「打开论文 2.5~9.7 秒 → 50 毫秒」是真的，
但**按页翻译这条路完全没吃到缓存** —— 实测每翻一页在事件循环上同步解析 PDF
**64~332 毫秒**，期间全站冻结。本轮接上缓存 + 丢进线程。

**依赖侧**：上一轮报告写「`pip-audit` → 无已知漏洞」，**一天后就过期了** ——
本机 Pillow 12.2.0 现在有 **40+ 个已知 CVE**，而 Pillow 正是用来打开
「用户上传的 PDF 渲染出来的图」和「图表截图」的，属于真实攻击面。

**方法侧**：这一轮最有价值的产出不是"抓了几个洞"，而是**两套自我纠错机制** ——
① 破坏性验证（把每处修复改回去，确认护栏**真的变红**）当场抓出 **5 条零覆盖护栏**；
② 执行代理之间出现**集成缺口**（原生侧加了白名单，网页侧没接线），
靠人工交叉比对两个代理的交付报告才发现。

## 4. 详细发现

### 4.1 🔴 C-1　批注重放自激循环 → 划词选区被清空

**位置**：`microbench/static/index.html` → `initAnnotationFeatures()`

**根因**（旧代码）：

```js
const obs = new MutationObserver(() => {
  if (!_annoState.items.length) return;
  setTimeout(reapplyAnnotations, 80);   // ← 没有 clearTimeout
});
obs.observe(list, { childList: true, subtree: true, characterData: true });
```

`reapplyAnnotations` 自己会改 DOM（`_clearAnnoMarks` 清标记 + `_wrapTextWithMark`
重新包 `<mark>`），而这个 DOM **正在被观察** → 改 DOM → 触发 observer → 再排一次
setTimeout → 再改 DOM …

**实测证据**（Playwright，真实页面）：

| 场景 | 结果 |
|---|---|
| 有 1 条可匹配批注，3 秒内 `reapplyAnnotations` 调用 | **32 次**（≈10.7 次/秒，永不停止） |
| 12 页 × 3000 字 × 24 条批注 | 3 秒占用 176ms 主线程，单次重放 11.9ms |
| **译文栏划词选区**（60 字符）→ 等 500ms | **选区长度变成 0** |
| 对照组（清空批注） | 选区 60 → 60 保持不变 |

**后果**：只要这篇论文有**一条能匹配上的批注**，用户在译文栏拖选划词时选区就被抹掉
→ `initReaderSelectionListener` 在 `mouseup` 读 `getSelection()` 拿到空 →
**划词答疑拿不到引文**。这正好打在项目主线「翻论文 → 翻译 → 划词 → 批注」的最后一步。

**修法**：`clearTimeout` 真防抖（200ms）+ **用户正在划词时不动 DOM**。

**护栏**：`microbench/_test_audit_2026_10_27.js`（node 跑 index.html 里的**真实源码**，
断言「5 次变更 → 只排 1 个定时器」和「划词中不重放」）。

### 4.2 🔴 C-2　平板 WebView 离源后仍持有原生桥

**位置**：`android/java/microbench/tablet/MainActivity.java`（`addJavascriptInterface`）
+ 平板 `index.html`（**无 CSP meta**）

**触发路径**：笔记/AI 答案里的 `[点我](https://evil)` → 用户点击 → `<a>` 无 `target`、
WebView 无 `shouldOverrideUrlLoading` → **顶层导航到外域** →
`shouldInterceptRequest` 对非 `appassets.androidplatform.net` 返回 null（走真实网络）→
恶意页拿到 `window.MicroBench` →

- `delete("01_Literature/x.pdf")` → 删用户原文
- `put(path, text)` → 往 vault 写内容（**会同步回电脑端，污染用户笔记**）
- `httpPost(url, body, auth)` → 以平板为跳板打用户内网 https

**修法**：① `shouldOverrideUrlLoading` —— 非本地源一律交给系统浏览器；
② 平板 `index.html` 加 CSP meta（`default-src 'self'`、`frame-src 'none'`、
`object-src 'none'`、`base-uri 'none'`，PDF.js 需要 `worker-src blob:`）；
③ `DavBridge.httpPost` 的目标主机收成白名单（原来只校验 `https://` 前缀 = 开放代理）。

### 4.4 🟠 H-2　限流器 `min_interval` 在并发下整体失效

**根因**：`llm.py` 限流器的间隔判据读的是 `_last_call_time`（**实际触发**时间，
在 sleep **之后**才更新），而**预留**写在 `_last_planned_time` ——
**间隔判据根本没用预留值**。

**实测**（真实类，5 线程、min_interval=6.0）：

```
CURRENT   gaps=['6.00','0.00','0.00','0.00']   ← 4/5 同时发出
FIXED     gaps=['6.00','6.00','6.00','6.00']
```

**连锁后果**：N 发齐射 → 打到上游每分钟上限 → 被 `is_quota_exhausted_error`
误判成「配额耗尽」→ `mark_degraded(kind="quota")` **全局降格 15 分钟**，
而用户额度其实还有。这正是 AGENTS.md 记过的「降格了但额度没耗尽」的机制来源。

**修法**：间隔判据改用**预留**时间。**验收标准是「每次实际触发间隔 ≥ min_interval」**。

### 4.5 🟠 H-3　按页翻译在事件循环上同步解析 PDF

**实测**（隔离测 `extract_page_text_with_glyphs`）：

```
Review of Magnetoelectric Sensors.pdf  9.3MB  page1=264.5ms  page5=112.3ms
2026_Sensors_&_Actuators...            7.8MB  page1=332.0ms  page5=192.6ms
2024_ACS_AMI_Luo_TMR...                7.1MB  page1=296.1ms  page5=236.5ms
```

`app.py` 的 `api_translate_page` 位于 `async def` 内、**无 `to_thread`、无 `await`**
→ 每翻一页就阻塞事件循环 0.1~0.35 秒，**期间全站冻结**（看板计数、3 个 SSE 答疑面板、
LAN 平板全部卡住）。36 页论文连翻 = 累计约 9 秒卡顿。

**修法**（两步）：
① **接上 `pdf_cache`** —— 缓存里的页结构与单页抽取**逐字一致**
（`extract_text_from_pdf` 每页调的就是 `_extract_page_text(page, glyphs)`，
和 `extract_page_text_with_glyphs` 同一个函数）→ 命中就是 ~0ms；
② 没命中就 `await asyncio.to_thread(...)` → 代价不变，但**不再冻结全站**。

### 4.6 🟠 H-6　`{ once: true }` 的语义是「任意键」

**实测**：

| 步骤 | 结果 |
|---|---|
| 打开快照弹窗 → 按 `a` → 按 Esc | 弹窗**没关**（`display` 仍为 `flex`） |
| 打开诊断弹窗 → 按 `x` → ×关闭 → 重新打开 → 按 Esc | **永久失效** |
| zen 开启 + 弹窗开着 → 按 `q` → 按 Esc | 弹窗没关、zen 仍在、**Esc 无人响应**（键盘陷阱） |

**修法**：统一走 `_wireModalEsc(overlay, closeFn)`（只认 Esc、关掉时摘干净、

### 4.9 🟡 跨设备共享文件的读-改-写

批注 JSON 住在**坚果云共享目录**。A 读 → A 合并 → A 写回；窗口里 B 写了一次
→ A 的写回**整文件覆盖** B 的内容。`_merge_annotation_lists` 只在内容层面合并，
**救不了整文件覆盖**。

**修法**：乐观 CAS —— 写之前再取一次 `(st_mtime_ns, st_size)` 指纹比对，
变了就重新读 + 重新合并（最多 3 轮）。窗口从「整个同步往返」缩到「一次文件读」。

### 4.10 🔴 数据面：三类「会真丢用户数据」的缺陷

这一组是**第四路审查**（前三轮明确未覆盖的模块）挖出来的，
特征是：**都不在服务端的安全边界上，而在「两台设备共享的数据」这条链路上**。

#### C-3　`auto_sync` 快进合并后回退失效 → 坏代码留在 HEAD 并被推给对方

**实测**（审查方用 upstream/work/other 三仓真实复现）：
对方 push `v2-BROKEN` → 本机 `git merge origin/main` 走**快进** →
跑测试 → 红 → `git merge --abort` → **rc=128 `fatal: There is no merge to abort`** →
**HEAD 仍是坏提交，文件内容仍是 `v2-BROKEN`**。

**后果比"回退失败"严重**：脚本报告 `action=tests_failed` 并声称"已回退合并（没有推）"，
但工作区实际已是坏代码；下一轮 `workspace_clean()` 因 HEAD 已推进而判定"干净"
→ **坏代码直接被 push 给对方**。
（备份分支 `backup-auto-sync-*` 一直存在，但流程里**从未被使用**。）

**修法**：先试 `git merge --abort` 并**检查返回码**；rc≠0 → `git reset --hard <合并前 SHA>`，
再失败用备份分支；回退后**校验** HEAD 与工作区，不符就**明确报"回退失败"**，
绝不能对外说"已回退"。新增 `result["rollback_ok"]`。

#### C-4　`pdf_cache` 缓存键缺「词典路径」→ `None` 与「文件不存在」撞键 → 脏缓存

**实测**：`cache_key(pdf, None)` 与 `cache_key(pdf, <不存在的路径>)` 走同一分支
`_sig()` → `[0, 0]` → **同一个键**。`dict=None` 时把词典内容从 `{}` 改成 100 字节
→ **键不变** → 词典认出的新符号不触发重抽 → **译文正文与原文不符**
（项目最严重的故障模式）。

**修法**：词典维度改成「**绝对路径 + 签名**」，`None` 用**显式哨兵** `"NO_DICT"`
→ 两者必然不同键。键变了 → 旧缓存一次性作废（可接受：缓存本就可再生）。

#### H-13　`merge_changes` 空 body 直接清空真实笔记

**实测**：vault 里 `01_Literature/real.md` 内容 `# real note\nimportant\n`，
变更包里 `body=""` + `baseHash` 正确 → 摘要 `written: [...]`
→ **文件内容变成 `''`**（原文全丢，**无冲突副本、无备份**），
且**绕过**了"两边都改 → 另存合并稿"的保数据策略。

**修法**：`body` 为空或仅空白 → 计入 `rejected`、**一个字都不落盘**。

> ⚠ **这是一处刻意的语义取舍**：平板端若确实"清空一篇笔记"再导出包，
> 电脑端**不会**被清空（原文保留）。宁可保留旧内容，也不丢数据。
> 若要支持"清空"，需要另走一条显式删除语义。

#### H-14 / H-15　`pdf_cache` 的 Windows 写入失败 + 结构不校验

**H-14 实测**：Windows 的 `ReplaceFile` 对**已被打开读**的目标文件返回
`ERROR_ACCESS_DENIED` → 6 线程并发写同一 key **32 次** `PermissionError`；
一读一写 2 秒 → **782 次**。后果是**缓存写不进去**（842x 加速在最需要它的并发场景拿不到）
且**读侧误判未命中**（用户每次都等 2.7~9.7 秒重抽）。

**修法**：缓存布局改成「**唯一文件名 + 按 mtime 取最新**」
（`<key>.<uuid4>.json`）→ **写侧永不替换任何已存在的文件** → 零竞争，
绕开了 Windows 的根因（不用「指针文件」是因为指针同样被频繁打开 → 一样撞权限错）。

**H-15 实测**：`pages` 只校验是非空 list，**不校验元素是 dict** →
写入 `{"pages":[123]}` → `read_cache` 返回 `[123]` → 下游 `p["text"]` 抛 `TypeError`
→ 端点 **500** 而不是"重抽一次"。

**修法**：命中后逐项验 `isinstance(p, dict) and isinstance(p.get("text"), str)`，
不合格当未命中。读缓存**永远不抛异常**这条既有行为保持。

#### H-16　`auto_sync` 的 12 个独立套件**不继承 conftest 沙箱**

上一轮 H-1 的修复（conftest 钉 `_sync_root`）**只覆盖了 pytest 那一半** ——
`auto_sync` 紧接着跑的 12 个 `python microbench/_test_x.py` **直接跑脚本**，
不加载 conftest → **无任何沙箱**。其中 `_test_regressions.py` → `test_bench.py`
直接对**真实 `BASE_DIR/01_Literature`** 做 `rglob` + `unlink`
（当前靠"内容标记 `MBTESTARTIFACT`"判据才没误删 —— **判据一旦回退就是删用户笔记**）；
`_test_lan.py` 则在**真实 app** 上跑，`lifespan` 会在**真实坚果云同步根建目录**。

**修法**：给独立套件加统一的沙箱入口（临时目录 + 钉 `_sync_root` + 钉 `BASE_DIR`）。

## 9. 结论与下一步

**VERDICT = PASS**

这个项目的安全底子依然很好：路径遍历 22 条专项 payload 全灭、XSS 经多轮加固后
**本轮复核无新发现**、凭据不进浏览器、依赖 CVE 已清零、跨设备红线一个没动。

**但这一轮的价值不在"又抓了几个洞"，而在四件事**：

1. **缺陷的重心从"安全边界"移到了"数据面"** ——
   批注重放让划词答疑拿不到引文；平板一个外链就能改用户的 vault；
   `auto_sync` 把坏代码推给对方；缓存键撞键让译文与原文不符。
   **这四条里只有一条是"安全漏洞"，另外三条是"功能坏了 / 数据没了"。**
   → 静态扫描和"看安全"是看不出它们的；**必须把真实页面跑起来、把真实数据打进去**。
2. **性能优化的收益会被"漏网的同类路径"吃掉** —— 10-27 早上那轮把 4 个端点
   改成同步 `def`，很棒；但 `find_pdf` 漏了，按页翻译那条路也完全没吃到缓存。
   **优化要按"路径"清点，不能按"端点"清点。**
3. **审计结论会过期** —— 一天前「无已知 CVE」，一天后 Pillow 40+ CVE。
4. **两套自我纠错机制各抓出真问题** ——
   破坏性验证当场抓出 **5 条零覆盖护栏**（AGENTS.md §4.62）；
   两个执行代理之间出现**集成缺口**（原生侧加了白名单、网页侧没接线），
   靠交叉比对交付报告才发现。
